# Benchmark baseline: 2026-10-08

Collected from the `/benchmark` page (`src/BenchmarkPage.tsx`) before any engine changes, as the reference point for ADR 0002.

- **Environment:** Chromium 152 (Claude desktop browser pane), macOS, 10 cores. Vite dev server.
- **Method:** each sample operation (default parameters from `src/sampleOperations.ts`) applied to a single copy of `warhol.jpg` at three sizes; 1 warm-up, then median of 5 runs. Each run reads back one pixel per output to force deferred canvas work to finish. Main thread.

## Observations

- **The slow operations are exactly the ones with JavaScript per-pixel loops** over `getImageData`/`putImageData`: `noise`, `rgbChannels`, `threshold`, and `halftone` (which calls `threshold`). They scale linearly with pixel count and are 10–40× slower than everything else at 2048².
- **Operations built on `ctx.filter` or compositing are already fast** (`blur`, `grayscale`, `invert`, `rotateHue`, `fill`, `stack`): the browser runs them on the GPU. Rewriting these in WebAssembly would likely make them slower.
- `printSet` cost comes from pattern construction and its large output canvas.
- ~0.6 ms is the floor (canvas allocation plus the pixel readback used to force completion).

Implications for ADR 0002: the first GPU/shader targets should be the per-pixel loops (`threshold`, `noise`, `rgbChannels`, and therefore `halftone`), not the `ctx.filter` operations. A filter gallery of a dozen 1024² previews of a cheap operation is already interactive; for a per-pixel-loop operation it costs ~150–300 ms.
